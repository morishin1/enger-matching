# ENGER business 企業ダッシュボード v2 — メニュー再設計・実装仕様

> `docs/business-portal-連携.md`（v1）の改訂版。v1 の確定メニューをベースに、
> **①シンプル化（企業の目的＝「人材がほしい」「案件がほしい」に直結）**、
> **②承認ゲート（承認をうけたらフル機能）**、**③候補者の全媒体一括管理**、
> **④AI面接（オプション）**、**⑤エージェントに紹介（モーダル）** を反映する。
> 本文書だけで実装に着手できる粒度で書く。

## 0. 大前提（v1 から変更なし）

- **シェル統一済み（enger-lp #96）**：企業ユーザーのメニューは **本リポジトリ（dx）の
  `src/components/Sidebar.tsx` の `CLIENT_NAV` が正**。画面本体も `/`（ClientHome）と `/portal/*`。
  → メニュー・画面の変更は **dx 側の実装作業**。enger-lp 側の作業は「旧シェル（スカウト送信=準備中 等）の撤去」と「チャット実URLの提供」のみ。
- **データの正は DX（Supabase `enger` スキーマ）**。企業に見せる人材情報は**常に匿名**（イニシャル＋スキル＋単価）。
- enger-lp 側でネイティブ実装する場合は、実装済みの公開API（§6）を使う（Bearer認証・`*.enger.jp` CORS）。

## 1. 設計原則 — 「企業が使いたい」の答え

管理メニューの羅列ではなく、企業の目的から逆算する：

| 企業の目的 | 提供する体験 |
|---|---|
| **人材がほしい** | 登録・掲載した瞬間からAIが匿名人材を提案。「会いたい」1クリックで担当が面談調整 |
| **案件がほしい**（SES企業） | 自社人材を「エージェントに紹介」→ ENGERの案件網（パートナー共有含む）でマッチング |
| 応募がバラバラで管理が大変 | **全媒体の候補者を1画面に一括**（LINE / 自社HP / 媒体メール / エージェント提案） |
| 面接工数を減らしたい | **AI面接（オプション）** で一次面接を自動化、結果は候補者ドロワーに表示 |

→ メニューは「成果が出る場所」を上に、設定系を下に。**7項目・迷わない構成**。

## 2. メニュー構成 v2（`CLIENT_NAV` 改訂）

| # | メニュー | 承認前 | 承認後 | 対応画面 |
|---|---|---|---|---|
| 1 | ダッシュボード | ○（トライアル案内＋充実度メーター） | ○ | `/`（ClientHome） |
| 2 | **人材をさがす**（旧: おすすめ人材） | 🔒 匿名ランキングのみ | ○ フル | `/portal/candidates` |
| 3 | **候補者・応募者**（旧: 選考管理） | 🔒 | ○ **全媒体一括**＋ドロワー | `/portal/selection` |
| 4 | 自社案件 | ○ **掲載申請まで可**（審査中表示） | ○ | `/portal/jobs` |
| 5 | **AI面接** 🏷オプション | 🔒 | ○（契約企業のみ表示） | `/portal/ai-interview`（新設） |
| ─ | （区切り線） | | | |
| 6 | チャット（担当に相談） | ○ | ○ | enger-lp 外部リンク（`NEXT_PUBLIC_LP_CHAT_URL`） |
| 7 | 自社情報 | ○ **入力可**（承認の助けになる） | ○ | `/portal/company` |

- **「スカウト送信」はメニューにしない**（v1どおり）。「人材をさがす」内の「会いたい」＝スカウト依頼。
- **「エージェントに紹介」もメニューにしない**。候補者・応募者ページ（および自社案件詳細）の
  **ボタン→モーダル**として設置（§4）。メニューを増やさずに動線を置く。
- AI面接は `app_settings`（または `companies` の契約フラグ）でオプション制御し、未契約企業には
  メニュー自体を出さない（「準備中」を見せない＝使えない機能で期待を裏切らない）。

### 承認ゲートの実装

- dx シェル内：`currentAccess()` の `status`（active/pending）で出し分け（既存パターン）。
- enger-lp ネイティブ実装時：`GET /api/public/me` → `{ status: "active"|"pending"|"none", approved }`。
- 🔒項目は**非表示ではなくロック表示**（クリックで「担当エージェントの承認後に利用できます。お急ぎの場合はチャットへ」）。
  承認で機能が増える体験＝承認を待つ動機になる。

## 3. 候補者・応募者（全媒体一括管理）

**1画面に、経路を問わずすべての候補者を集約**する。

- 一覧の1行：イニシャル / 職種 / スキルタグ / 希望単価 / ステージ / **経路バッジ** / 受信日。
- **経路（source）バッジ**：`エージェント提案`（既定）・`LINE`・`自社HP応募`・`Indeed`・`エン転職` 等。
  データ源は `proposals.source`（実装済み。`GET /api/public/proposals` が返却）＋
  `enger.applications`（LP応募）。媒体の追加は §7 のフェーズで拡張。
- フィルタ：経路 / ステージ / 案件。既定は「対応が必要な順」（新着→企業未回答）。
- **詳細はドロワー**（右スライド。ページ遷移しない）：
  - 匿名プロフィール（スキル全件・経験・リモート・稼働・年代・国籍・マッチ度）
  - 選考ステージのタイムライン
  - **AI面接の結果**（オプション契約時。§5）
  - アクション：**会いたい / 検討中 / ミスマッチ**（`POST /api/public/feedback`）
- ヘッダー右に **「エージェントに紹介」ボタン**（§4 モーダル）。

## 4. エージェントに紹介（モーダル）

「人材を登録」ではなく「**エージェントに紹介**」が正しい語彙（人材マスタへの直接登録はしない。
エージェントが内容を確認してから登録する）。

- 入力項目：`GET /api/public/form-defs` の `forms.candidate`（氏名任意・イニシャル・職種・スキル・単価・稼働等）。
- **AIボタン**：経歴テキスト貼り付け → `POST /api/public/ai-draft {kind:"candidate", text}` → 下書き自動入力。
- 送信：`POST /api/public/candidate-referrals` → `enger.client_referrals` に保存・**Slackで社内へ即時通知**。
- モーダル下部に紹介履歴＋対応状況（new=未対応 / contacted=対応中 / registered=人材登録済 / closed=見送り）。
- 完了メッセージ：「担当エージェントが内容を確認し、マッチする案件をおさがしします」＝**案件がほしいSES企業への価値**を明示。

## 5. AI面接（オプションモジュール）

既存のAI面接ツールを企業向けオプションとして組み込む。**連携仕様の確定に以下のヒアリングが必要**：

- [ ] AI面接ツールの面接URL発行方法（API有無・認証方式）
- [ ] 結果（評価レポート・録画URL）の取得方法（API / Webhook / メール）
- [ ] 課金単位（企業月額 / 面接1回ごと）

### 段階実装（ヒアリング前でも進められる順）

1. **Phase A（手動リンク）**：候補者ドロワーに「AI面接を依頼」ボタン → 担当（ENGER営業）へ通知
   （client_referrals と同じSlack通知パターン）。営業が面接URLを手動発行して候補者へ送付。
2. **Phase B（結果表示）**：DX に `enger.ai_interviews`（proposal_id, status, score, report_url, video_url,
   summary, created_at）を追加し、結果をドロワー内に表示。`GET /api/public/proposals` のレスポンスに
   `ai_interview` を併載。
3. **Phase C（API直結）**：AI面接ツールのAPIで発行〜結果取得を自動化。Webhook受け口
   `POST /api/public/ai-interview-webhook`（署名検証つき）を DX に追加。

## 6. 実装済み公開APIリファレンス（dx 側・本リポジトリ）

すべて `Authorization: Bearer <Supabaseアクセストークン>`・CORS `*.enger.jp`・`cache: "no-store"`。

| API | 用途 | 承認前(pending) |
|---|---|---|
| `GET /api/public/me` | ステータス照会（メニュー出し分け） | ○ |
| `GET /api/public/form-defs` | フォーム定義（会社/案件/人材。DXと同一項目） | ○（認証不要） |
| `GET/PUT /api/public/company-profile` | 自社情報の取得/保存（企業管理 companies へ連動） | ○ |
| `GET/POST /api/public/jobs` | 自社案件の一覧/掲載申請（審査フロー） | ○ |
| `POST /api/public/ai-draft` | AI下書き（company=HP/法人番号, job/candidate=テキスト） | ○ |
| `GET /api/public/proposals` | 候補者・応募者一覧（匿名・source・FB併載・ドロワー詳細込み） | ✗ 403 |
| `POST /api/public/feedback` | 会いたい/検討中/ミスマッチ | ✗ 403 |
| `GET/POST /api/public/candidate-referrals` | エージェントに紹介＋履歴 | ✗ 403 |
| `GET /api/public/job-detail` | （フリーランス向け）案件詳細＋面談済ゲート | — |

マイグレーション（SQL Editor・冪等）：`supabase/business-portal-api.sql`（corporate_no）、
`supabase/client-referrals.sql`（紹介テーブル）、`supabase/ai-interviews.sql`（AI面接テーブル＋契約フラグ
`app_users.ai_interview`）。AI下書きの法人番号対応は env `GBIZINFO_TOKEN`。

## 7. 媒体一括管理のロードマップ

1. **Phase 1（実装済み）**：`proposals.source` の経路バッジ表示（LINE / エージェント等）。
2. **Phase 2**：媒体の応募通知メール（Indeed・エン転職・リクナビNEXT等）を DX の既存 Gmail 取込
   パイプライン（inbox_emails → 登録）で**媒体パーサー**として拡張し、`source="indeed"` 等を付与して
   candidates/proposals へ自動投入。※DXに取込基盤があるため新規開発は「媒体別パーサー」のみ。
3. **Phase 3**：媒体公式APIとの直接連携（媒体ごとに契約・審査が必要なため最後）。

## 9. モデル推奨（Claude Code での実装時）

| 作業 | 推奨モデル | 理由 |
