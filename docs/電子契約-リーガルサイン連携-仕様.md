# 電子契約（リーガルサイン連携）— 実装仕様

> 2026-07-29 決定：**電子契約はリーガルサイン等の電子署名サービスを利用して機能として実装する**。
> 法人LP（enger.jp/business）はこれを前提に「電子契約 締結〜請求まで完結」「電子契約 / 与信不要」を
> 訴求しており、Feature 04「契約・進捗管理」もこの機能を指す。**LPの記載は変更しない。**
>
> 本書は着手前の設計メモ。未確定事項（§6）はサービス側の仕様確認が必要。

## 0. いま何があって、何が無いか

土台はすでに dx（本リポジトリ）にある。**足りないのは「署名そのもの」と「3者への露出」**。

| 要素 | 現状 | 置き場所 |
|---|---|---|
| 稼働契約の実体 | ✅ ある | `enger.engagements` |
| 契約ステータス・注文書ステータス | ✅ 列あり（自由文） | `engagements.contract_status` / `po_status` |
| 更新期限・更新ステータス | ✅ 列あり | `engagements.renewal_due` / `renewal_status` |
| 勤怠・請求（月次） | ✅ ある | `enger.billing_tasks`（勤怠/請求書＋Storage） |
| **電子署名の送信・締結** | ❌ 無い | — |
| **締結済み書面の保管・参照** | ❌ 無い（billing の Storage は勤怠/請求書用） | — |
| **企業・フリーランスの画面への露出** | ❌ 無い（現在サイドバーは「準備中」表示） | enger-lp |

`contract_status` は現在**自由文**。電子契約を入れるなら、ここを署名の進行状況と機械的に連動させる必要がある。

## 1. 3者から見た電子契約

締結は「マッチングが決まった後」の最後の工程。要件定義§13の共通ステータスの
`条件調整 → 契約 → 参画` の「契約」がこの機能にあたる。

```
エージェント（dx）            フリーランス（enger.jp）        企業（enger.jp/business）
 契約内容を確定して送信 ──▶  受信・内容確認・署名 ─┐
                            ├──▶ 双方署名で締結 ──▶ 契約・請求で締結済み書面を参照
 進行状況を監視・催促  ◀────────────────────────┘        （更新期限のアラートも）
```

- **署名する当事者**は案件ごとに変わる（ENGER↔フリーランス／ENGER↔企業／三者）。
  誰が署名者かを契約レコードに持たせる（§3の `parties`）。
- **原価・粗利はエージェントのみ**（情報公開ルール§15.3）。契約書面に原価が載る場合、
  企業・フリーランスに見せる版を分ける必要がある。→ §6 で要確認。

## 2. 画面と操作

### エージェント（dx・主導する側）
- 稼働管理（engagement）の詳細に「**電子契約**」ブロックを追加
  - 契約テンプレート選択（NDA／業務委託基本契約／個別契約・SOW／注文書）
  - 署名者の指定（メール）→「送信」
  - 進行状況（下書き／送信済み／一部署名／締結済み／却下／期限切れ）と各当事者の署名日時
  - 締結済みPDFのダウンロード
- 「未締結のまま稼働開始日を過ぎている契約」をタスク・要対応に出す（既存の要対応と同じ枠）

### フリーランス（enger.jp）
- サイドバー「契約・報酬」（現在は**準備中**表示）を有効化
  - 署名待ちの契約を最上部に（未署名バッジ）→ 署名画面へ
  - 締結済み契約の一覧・PDF、稼働報告、請求

### 企業（enger.jp/business）
- サイドバー「契約・請求」（現在は**準備中**表示）を有効化
  - 契約中のメンバー、締結済み書面、更新期限、請求
- ホームの「今日のおすすめアクション」に「署名待ちの契約が N件」を追加

## 3. データ設計（案）

`supabase/e-contracts.sql`（冪等）として追加する想定。

```sql
create table if not exists enger.contracts (
  id             uuid primary key default gen_random_uuid(),
  engagement_id  uuid references enger.engagements(id) on delete cascade,
  kind           text not null,          -- nda / master / sow / po
  provider       text not null default 'legalsign',
  provider_doc_id text,                  -- 電子署名サービス側の文書ID
  status         text not null default 'draft',
                 -- draft / sent / partially_signed / completed / declined / expired / canceled
  parties        jsonb not null default '[]',
                 -- [{role:'enger'|'freelance'|'client', name, email, signed_at}]
  title          text,
  amount         numeric,                -- 契約金額（表示用。原価は含めない）
  period_start   date,
  period_end     date,
  signed_pdf_path text,                  -- Storage（署名付きURLで配布）
  sent_at        timestamptz,
  completed_at   timestamptz,
  created_by     uuid,
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);
create index if not exists contracts_engagement_idx on enger.contracts (engagement_id);
create index if not exists contracts_status_idx on enger.contracts (status);
alter table enger.contracts enable row level security;
grant all on enger.contracts to service_role;

create table if not exists enger.contract_events (
  id          uuid primary key default gen_random_uuid(),
  contract_id uuid references enger.contracts(id) on delete cascade,
  event       text not null,            -- sent / viewed / signed / declined / completed
  actor_email text,
  payload     jsonb,                    -- Webhook の生データ（監査用）
  created_at  timestamptz not null default now()
);
```

- `engagements.contract_status`（既存の自由文）は**contracts の最新状態から自動更新**する。
  手入力も残す（電子契約を使わない紙の契約が実在するため）。
- 締結済みPDFは**署名付きURL運用**（billing バケットの public 運用は踏襲しない。契約書面は機密）。

## 4. 連携方式

```
dx（サーバーアクション）──送信──▶ リーガルサイン API
                                      │
        Webhook ◀── 署名/締結イベント ──┘
          ↓
  contract_events に記録 → contracts.status 更新 → engagements.contract_status 同期
          ↓
  企業・フリーランスへ通知（アプリ内＋メール。要件定義§14の通知対象に「契約期限」あり）
```

- **公開API**（enger-lp から使う分）：
  - `GET /api/public/contracts` … 自分（企業／フリーランス）に関係する契約一覧
  - `GET /api/public/contract-file?id=` … 締結済みPDFの署名付きURLを返す
  - 署名操作自体は**電子署名サービスの署名画面へリダイレクト**（自前で署名UIは作らない）
- Webhook 受け口：`POST /api/public/econtract-webhook`（**署名検証必須**。AI面接 Webhook と同じ方針）

## 5. 実装フェーズ

| Phase | 内容 | 依存 |
|---|---|---|
| A | `enger.contracts` / `contract_events` 追加、dx の稼働詳細に契約ブロック（**手動運用**：締結済みPDFをアップロードして状態管理） | なし・すぐ着手可 |
| B | リーガルサイン API で送信・状態取得、Webhook で自動同期 | §6の確認 |
| C | 企業・フリーランスの「契約・請求」「契約・報酬」を公開（サイドバーの準備中を解除）、署名待ち通知 | A・B |
| D | 更新期限アラート（`renewal_due`）と自動更新契約の再送 | C |

**Phase A は外部仕様に依存しないので、先に入れて運用を回せる。**

## 7. やらないこと

- 自前の署名UI・電子証明書の取り扱い（サービスに委ねる）
- 原価・粗利を含む書面を企業・フリーランスへ出すこと（§15.3）
- 紙の契約の廃止（電子と併存させる。`contract_status` の手入力を残す理由）
